# 03 · Configuration: NBT · storage · scoreboards · tags · mcdoc

中文: `docs/03-配置.md`

This page is for people who want to hook up their own datapack or write scripts that generate mobs. Pure play does not need it.

## 1 · Entity NBT (the `auto_init` entry point)

Write custom data into `data.dvh` via `/summon` or `data modify entity`, and it is read automatically on the first tick:

| Key | Type | Required | Description |
|---|---|---|---|
| `max_health` | double / string | ✅ | Max virtual health, **in HP units** (`40d`, `40`, `"40"` all work) |
| `health` | double / string | ✅ | Initial health, HP units (may differ from `max_health`, for a "mob that is already wounded") |
| `on_death` | string | — | Death callback command string (no leading `/`) |

```
/summon minecraft:zombie ~ ~ ~ {data:{dvh:{max_health:40d, health:40d, on_death:"say died"}}, NoAI:1b}
```

After writing `data.dvh`, do not also call `api/create` manually in the same tick. `auto_init` calls it for you, and a repeat call `return fail`s.

## 2 · storage layout

### `doom.vh:ctx` · runtime data (core)

The key names are flat, not nested objects. That is to work with macro expansion and the `data get` form:

| Key | Written by | Description |
|---|---|---|
| `with` | `api/*` | API input forwarding slot: `{max_health, health, on_death?}` |
| `uid0` … `uid3` | `trigger_death` | Kill attribution: the four ints of `last_hurt_by_mob`'s UUID |
| `uid_hex` | `internal/uuid_join` | The hex string joined from those four ints (for `damage ... by <uuid>`) |
| `on_death` | `trigger_death` | The callback command string for this death |
| `state` | `api/set_invulnerable` | `0` = damageable, `1` = invulnerable |
| `_` | `api/*` | Macro parameter scratch slot (the key name is a bare underscore, written as `"_"` in mcdoc) |
| `trigger` | `api/apply_trigger` | Equipment NBT round-trip staging: read `equipment.mainhand`/`saddle` → rewrite → write back → `data remove` |
| `b0` … `bf` | `internal/uuid_hex` | UUID byte splitting (16 slots) |
| `h0` … `hf` | `internal/uuid_hex` | The two hex characters of each of those 16 bytes (used to join `uid_hex`) |

### `doom.vh:const` · read-only constants

| Key | Description |
|---|---|
| `hex_chars` | A lookup array of the 256 two-character hex strings (`"00"` … `"ff"`), used for the UUID→hex conversion |

### `doom.dbb:ctx` · runtime data for the health bar (`doom.bossbar`)

| Key | Description |
|---|---|
| `id` | Health bar identifier string (used to tell bars apart on create / sync / delete) |
| others | Macro parameter staging (the same `_` pattern as the core) |

> All three storages are globally shared scratch workspaces. Execution is serial within a tick, so it is safe.
> But do not reuse these keys from another datapack: the values you write are liable to be overwritten by the next API call.

## 3 · Scoreboard list

`__load__` creates these objectives (all `dummy`):

| Scoreboard | Type | Description |
| ----- | --- | ---- |
| `dvh.health` | entity | Current virtual health (mHP) |
| `dvh.max_health` | entity | Max virtual health (mHP) |
| `dvh.total_damage` | entity | Cumulative damage taken (mHP) |
| `dvh.total_healing` | entity | Cumulative healing (mHP) |
| `dvh.player_damage` | entity | Damage dealt by players (mHP) |
| `dvh.rem_damage` | entity | Damage remainder (carry compensation) |
| `dvh.rem_heal` | entity | Healing remainder |
| `dvh.pp` | entity | Percentage threshold (lower bound) `[0,100]`, which you set to draw bands |
| `dvh.pp_max` | entity | Percentage threshold (upper bound) `[0,100]` |
| `dvh.prev_hp` | entity | Previous tick's health probe value (×2200) |
| `dvh.damage_mult` | entity | Damage multiplier (×1000, default `1000` = 100%) |
| `dvh.saddle_bonus` | entity | Equipment bonus cache |
| `dvh.temp` | `#virtual` (fake player) | Internal temporary calculation |
| `dbb.temp` | `#virtual` (fake player) | Internal health bar temporary identifier |

When changing these values note: writing `dvh.health` / `dvh.max_health` **directly into the scoreboard does not sync into the system internals** (internally, storage/attributes are authoritative);
use APIs such as `api/set_health` / `api/set_max_health`.
`dvh.pp` / `dvh.pp_max` / `dvh.damage_mult` are the opposite — they are meant to be written directly by you (`damage_mult` can also go through `api/set_damage_mult`).

## 4 · Tags

| Tag | On whom | Description |
| ---- | ---- | ---- |
| `virtual_health_entity` | entity | Virtual-health entity marker; every selector relies on it |
| `dvh.invulnerable` | entity | Invulnerable-state marker (added by `set_invulnerable {state:1b}`, removed by `{state:0b}`) |
| `dbb.has_bossbar` | entity | Health bar already bound (used by `doom.bossbar`) |

Entity type tag: `#doom.virtual.health:riding` (pig / horse / donkey / mule / skeleton horse / zombie horse / camel / strider).
`api/apply_trigger` uses it to decide whether the vitality enchantment goes in the mainhand or the saddle slot.

Function tags (`#doom.virtual.health:<name>`, so other datapacks can call them with `function #...` without knowing mcfunction paths):
`add_health` · `add_health_pct` · `add_max_health` · `add_max_health_pct` · `get_health` · `get_health_mhp` ·
`get_max_health` · `get_max_health_mhp` · `get_percentage` · `get_player_damage` · `get_total_damage` · `get_total_healing` ·
`load` · `remove` · `set_health` · `set_health_pct` · `set_invulnerable` · `set_max_health` · `tick`.

The load hooks are attached to `#minecraft:load` / `#minecraft:tick`, live as soon as the pack is installed:

```
# load → doom.virtual.health:__load__ + doom.bossbar:__load__
# tick → doom.virtual.health:core/main + doom.bossbar:core/main
```

## 5 · mcdoc completion (optional, used in the editor)

The pack contains 3 mcdoc files:

| File | Completes |
| ---- | ---- |
| `mcdoc/doom.virtual.health.mcdoc` | `data modify storage doom.vh:ctx ...`, declaring every slot in the table above, so a mistyped key name is flagged on the spot |
| `mcdoc/doom.bossbar.mcdoc` | `data modify storage doom.dbb:ctx ...` |
| `mcdoc/doom.virtual.health.tags.mcdoc` | Function tag reference |

How to use it: install the Spyglass extension plus `Misodee.vscode-mcdoc` in VS Code, open the whole `doom.virtual.health/` directory as the workspace,
and typing `data modify storage doom.vh:ctx ` will show key suggestions; typing `data:{dvh:{` also suggests `max_health` / `health` / `on_death`.
The example is written in the pack's `function/mcdoc.mcfunction`; copy from it freely.

> Remember to sync the mcdoc when you add a runtime key, otherwise the editor marks the key as "unknown" (the runtime is unaffected).

## 6 · Performance and write frequency (what to know when hooking up your own pack)

- `core/main` is attached to `#minecraft:tick` and each tick works only on `@e[tag=virtual_health_entity]`, so unregistered entities cost nothing;
- Each entity costs one `execute store result` sample plus one `scoreboard` comparison per tick — constant level;
- `doom.bossbar:core/main` is the same, and only handles entities with `dbb.has_bossbar`;
- To spend a little less: mobs whose `on_death` is left empty skip a stretch of UUID tracking (tracking only runs when kill attribution is needed).
