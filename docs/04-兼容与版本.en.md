# 04 · Compatibility and versions

中文: `docs/04-兼容与版本.md`

## 1 · What this pack declares

Starting from 1.21.9, MC tightened the datapack metadata rules: `pack.mcmeta` must declare `min_format`/`max_format`,
and those must match `supported_formats` value for value, otherwise the whole pack is rejected. 1.21.5–1.21.8 do not recognise those two fields.
That is why this pack is split into two variants. The command layer is byte-identical; only `pack.mcmeta` and `enchantment/vitality.json` differ.

Primary build `v3.1.0` (1.21.5 – 26.2):
```json
{
  "pack": {
    "pack_format": 71,
    "supported_formats": { "min_inclusive": 71, "max_inclusive": 107 },
    "min_format": [71, 0],
    "max_format": 107,
    "description": "§cDVH v3.0 §7+ §9DBB\n§7Scale 22, max_health up to 95325"
  }
}
```

26.3 variant `v3.1.0-mc26.3` (26.3 only, pure new form):
```json
{
  "pack": {
    "min_format": [121, 0],
    "max_format": 121,
    "description": "§cDVH v3.0 §7+ §9DBB\n§7Scale 22, max_health up to 95325"
  }
}
```

- Why the lower bound is 71: 71 = the data pack format of 1.21.5. The pack's code uses `equipment:{}`, introduced only in 1.21.5,
  so the source pack's original `min_inclusive: 48` was wrong ✗. v3.1.0 tightens it to 71, matching the real capability.
- Why the upper bound is 107: 107 = the data pack format of 26.2. 26.3 = 121, which belongs to the 26.3 variant.
- Why the 26.3 variant drops `pack_format`/`supported_formats`: on a real machine MC reports
  `Pack key supported_formats is deprecated starting from pack format 82. Remove supported_formats from your pack.mcmeta.`
  ⇒ it triggers as soon as the declared range reaches 82+. A pure 82+ pack may only keep `min_format`/`max_format`.
- The `DVH v3.0` and `DBB` (Doom Bossbar) in the description string are in-pack display names, kept in their original form by convention.
  The release number is the repo's Release tag, currently `v3.1.0`. The two refer to the same version.

## 3 · Upgrading / downgrading

### Upgrading (e.g. a future v3.0.1)

1. Note down the version you are currently running (the zip filename under `dist/`);
2. Run `/function doom.virtual.health:__unload__` to strip everything clean first, so no old tags or health bars linger on entities;
3. Delete the old directory, put the new `doom.virtual.health/` in place, run `/reload`;
4. To give old mobs in the world virtual health again: re-run `auto_init` on them (`/data modify entity … data.dvh …`), or `api/create`.

### Downgrading

There is no "data migration" step in the pack; downgrading is the same as upgrading: strip clean → swap the directory → `/reload`.
A downgrade may cause fields only present in newer versions to be ignored, for example a changed meaning of a newly added `on_death`. Back up the world first.

### Which file edits need a server restart

| Change | Is `/reload` enough |
|---|---|
| `function/**/*.mcfunction` | ✅ `/reload` is enough |
| `tags/function/*.json` (including `#minecraft:load` / `#minecraft:tick`) | ✅ `/reload` is enough |
| `enchantment/vitality.json` | ❌ **A server restart is required** (the enchantment registry is only read at startup). Using the wrong variant on 26.3 blows up right here |
| `pack.mcmeta` | Needs the datapack reloaded (re-enter the world in single-player; on a server restart if `/reload` did not take effect) |

## 4 · Version-numbering rules (adopted by this repo from v3.0.0)

```
v<MAJOR>.<MINOR>.<PATCH>              release       e.g. v3.0.0
v<MAJOR>.<MINOR>.<PATCH>-beta.<N>     prerelease    e.g. v3.1.0-beta.1
v<MAJOR>.<MINOR>.<PATCH>-rc.<N>       candidate (optional)  e.g. v3.1.0-rc.1
```

| Digit | When it goes up |
|---|---|
| **MAJOR** | Players or modpack authors must take action to keep using it (storage fields renamed, function paths renamed, pack structure changed, a different experimental toggle needed), or the first adaptation after a Minecraft major-version change |
| **MINOR** | Backwards-compatible new capability, new content: a new customisable field, a new API, a new preset |
| **PATCH** | Bug fixes, performance, docs, and behaviour-preserving repacks (clearing ghost files, recomputing sha256, correcting the in-pack description, housekeeping) |

The Minecraft version does not go into the version number: it is written only in `pack.mcmeta` and in sections 1–2 above, and it does not appear in attachment names either.
That way, changing MC version does not mean renaming every historical attachment.

Release boundary: if any single byte of an artifact (the pack body or the zip) changes, you must bump PATCH and re-publish the attachment. Only docs or metadata changes may be committed directly without a release.
One version number maps to exactly one artifact and is never reused; published tags are not moved and not deleted.

## 5 · Known "cannot be changed" parts

These are determined by vanilla mechanics, not bugs (the full list is in the Edge Cases section of the repo root README):

- A single-tick burst of more than 512 HP of damage is truncated by the probe (E6);
- A single-tick burst of more than 512 HP of healing is lost (E7);
- Entities in unloaded chunks do not take part in tick detection and their health does not change (E8);
- An entity `/kill`ed directly does not trigger `on_death` (E10);
- Player entities are supported for virtual health, but dropping XP or inventory on death is vanilla behaviour beyond this pack's control (E12).
